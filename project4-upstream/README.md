# 项目 4：上游贡献 + 总结（约 2 周）

## 目标

完成至少一个被接受（或至少被认真 review）的上游 PR，并把前四个项目的经验沉淀为可阅读的系列文档。

## 贡献流程

1. **选题**：`good first issue`、文档错误、测试补齐、小 bug。不要从调度器/内核开始。
2. **复现**：在固定 commit 的 `external/` 中复现，记录步骤、环境、失败输出。
3. **定位**：找到最小改动点，记录相关文件与函数。
4. **修复 + 测试**：最小改动，附单测或可复现验证脚本。
5. **本地检查**：跑仓库要求的 lint / 格式化 / 相关测试（以 `CONTRIBUTING.md` 为准）。
6. **提交 PR**：描述包含问题、复现、改动、验证命令、影响面、兼容性。
7. **回应 review**：优先补测试与文档，不做无关重构。

## PR 检查清单

- [ ] 基于最新上游主分支（或仓库要求的基线）
- [ ] 一个 PR 只做一件事
- [ ] 有测试；无测试时说明原因
- [ ] 本地跑过 lint / 相关测试
- [ ] PR 描述可独立复现
- [ ] 没有提交无关格式化、生成文件、权重
- [ ] 记录了基线 commit 与验证命令

## 笔记结构

```text
project4-upstream/
├── notes/
│   ├── 01-candidate-issues.md   # 候选 issue 与初判
│   ├── 02-pr-<编号>.md          # 每个 PR 的问题/改动/验证/经验
│   └── 03-retrospective.md      # 复盘
└── patches/                     # 导出的 patch（如有）
```

每条 PR 笔记至少包含：

- 链接、状态、review 意见
- 问题根因
- 改动前后行为
- 验证命令与输出
- 学到的仓库规范（测试、lint、CI、commit message）

## 总结文档（4 篇）

建议按项目写，每篇包含：目标、做法、数据、结论、踩坑、源码收获。

1. 基线：vLLM 请求生命周期与 continuous batching
2. 网关：TP vs DP、prefix caching、调度参数
3. Omni：多阶段流水线与流式音频
4. 二次开发：一个小改动如何走完上游流程

## 验收标准

- [ ] 至少 1 个 PR 提交，CI 通过
- [ ] PR 描述与笔记完整、可复现
- [ ] 系列文档可被他人独立阅读
- [ ] 复盘写清：哪些判断错了、下次如何改进

## 心态

- 第一次 PR 被要求修改是常态；review 意见是学习材料
- 文档与测试类贡献同样有价值
- 不为了「有 PR」而提交低质量改动
