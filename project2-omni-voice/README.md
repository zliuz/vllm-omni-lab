# 项目 2：vLLM-Omni 实时语音助手（约 3 周）

## 目标

麦克风/网页录音 → 流式送入 Omni 模型 → 流式返回文本 + 语音播放。通过这个项目理解 vLLM-Omni 的**多阶段流水线**。

## 数据流

```text
麦克风 → 分块音频 → vLLM-Omni 服务
                         ├── 音频编码器
                         ├── thinker（文本理解/生成）
                         ├── talker（语音 token）
                         └── 音频 decoder → 波形
        ←──────── 流式文本 + 流式音频 ────────┘
```

## 三个里程碑（每个都可独立验收）

### M1：离线跑通（2–3 天）

- 按 `external/vllm-omni` 的 `examples/` 跑 Qwen2.5-Omni-3B 的音频理解（音频进、文本出）
- 记录：启动命令、显存占用、单条音频延迟
- 产出：`scripts/serve_omni.sh` + 一段可复现的命令

### M2：流式对话（约 1 周）

- 把 M1 改造成流式输入/输出
- 用 Python 客户端分块发送音频，接收流式文本
- 测首包延迟（音频发送完成 → 第一个文本 token）
- 产出：`client/cli_stream.py`

### M3：实时语音助手（约 1 周）

- 浏览器或 CLI 录音 + 播放
- 文本与音频同步播放
- 尝试打断（barge-in）：用户再次说话时停止当前输出
- 产出：可演示 demo + 延迟瀑布图

## 模型与显存（2 × 4090）

| 模型 | 精度 | 显存 | 部署 |
|---|---|---|---|
| Qwen2.5-Omni-3B | bf16 | ~7GB | 单卡，首选 |
| Qwen2.5-Omni-7B | bf16 | ~17GB+ | 单卡紧张，建议 TP=2 |
| Qwen3-Omni-30B-A3B | bf16 | ~60GB | **放不下**；仅仓库支持 FP8/AWQ 时再尝试 |

**先从 3B 开始**。7B 若 OOM：降 `--max-model-len` → 降并发 → 再考虑量化。

> Omni 模型的启动入口、参数与支持列表以 `external/vllm-omni` 的 README 和 `examples/` 为准，不要照搬文本模型的命令。

## 要搞懂的机制

1. 多阶段如何定义与串联（stage / pipeline 抽象）
2. 音频/视觉输入如何编码成模型 token
3. thinker 与 talker 的分工
4. 音频 token 如何解码为波形，流式如何切块
5. 各阶段耗时占比，瓶颈在哪里

## 指标

- **首包延迟**：用户说完 → 第一个文本 token（目标 < 1.5s，4090 上）
- **首音频延迟**：用户说完 → 第一段可播放音频
- 每秒生成音频时长 / 实时率（RTF）
- 并发 1 / 2 / 4 时的延迟与显存

## 验收标准

- [ ] 真实录音提问，模型能正确理解并回答
- [ ] 文本与语音均为流式，不是等全部生成完再播放
- [ ] 有明确的阶段耗时瀑布图和首包延迟数字
- [ ] 7B（或 3B）在目标配置下连续运行 ≥ 1 小时不 OOM
- [ ] 异常路径有处理：麦克风断开、服务超时、中途取消

## 风险

- **vLLM-Omni 迭代快**：固定 commit，并把版本写进 README；API 变化时先看 examples 再改代码
- 流式音频的块大小影响延迟与爆音，需要调参
- 浏览器录音采样率与模型要求可能不一致，先做重采样验证
